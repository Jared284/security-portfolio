# Lab 04 – SSH Authentication Log Triage

## Objective
Investigate repeated SSH authentication failures to determine whether observed activity represents benign user error or automated brute-force attack behavior.

---

## Data Sources
- `/var/log/auth.log`
- OpenSSH authentication events generated by sshd

---

## Initial Signal
Multiple failed SSH authentication attempts were observed originating from a single source IP within a short time window.

This pattern triggered further investigation to determine intent and risk.

---

## Analysis and Triage
Authentication logs were reviewed to assess the nature of the failed login activity.

Key observations included:
- Repeated failed authentication attempts from the same source IP
- Targeting of invalid or non-existent usernames
- High frequency of failures over a short time interval

Individual failed login attempts were treated as low-signal events.  
Aggregation by source IP and time window revealed a consistent pattern indicative of automated behavior rather than user error.

---

## Assessment
The volume, frequency, and targeting of invalid usernames strongly suggest automated SSH brute-force probing rather than legitimate authentication mistakes.

This activity represents a credible security threat requiring mitigation.

---

## Response and Outcome
- The source IP exceeded the configured authentication failure threshold
- fail2ban automatically enforced a ban on the offending IP
- Subsequent SSH connection attempts from the source IP were blocked

This confirmed end-to-end detection and response functionality.

---

## Analyst Takeaways
- Raw authentication logs are noisy; aggregation reveals attacker intent
- Repeated failures across time are higher-signal than isolated events
- Effective detection depends on reliable log ingestion and network reachability
- Automated controls are only effective when underlying telemetry is complete
